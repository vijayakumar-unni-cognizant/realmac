HIGH CQ-08 — innovation-card proxy is missing imageDelegate — zero card images render

Issue
Every render of a card logs: 'In order for image rendering delegation to work correctly you need to set up the imageDelegate property on the /apps/realmac/components/innovation-card component; its value has to point to the resource type of an image component.' All 4 cards render with zero .cmp-teaser__image block.
Evidence
grep of C:\AEM\author\crx-quickstart\logs\error.log around the fresh install window (20:11:32-20:11:50) shows 20+ repeated ERROR lines from com.adobe.cq.wcm.core.components.internal.models.v1.AbstractImageDelegatingModel naming /apps/realmac/components/innovation-card specifically; cross-checked against the rendered HTML for card_0..card_3 which contain a .cmp-teaser__content block but no .cmp-teaser__image block at all (contrast with the hero teaser, which DOES render its image correctly and DOES declare imageDelegate on its own realmac/components/teaser node).
Cause
Core Component's image-delegation lookup reads the imageDelegate cq:Component property from the requested resource's OWN component node, not walked up the sling:resourceSuperType proxy chain. realmac/components/teaser declares imageDelegate="realmac/components/image" on itself; innovation-card (a further proxy of teaser) does not redeclare it, so the property is absent for innovation-card specifically.
Recommended fix
Add imageDelegate="realmac/components/image" to innovation-card's own .content.xml, mirroring the property already declared on realmac/components/teaser.

HIGH CQ-09 — innovation-card's own nested Content Policy never applies at runtime

Issue
Despite (a) the policy node /conf/realmac/settings/wcm/policies/realmac/components/innovation-card/policy_landing_card_teaser existing live with correct titleType=h3, imageDelegate, and cq:styleGroups (styleClasses=cmp-teaser--innovation-card, styleId=20260828104), and (b) the template's policy mapping tree correctly pointing innovation-card -> that exact policy path — all 4 rendered cards still show a literal <h2> tag (titleType never applied) and ZERO occurrences of cmp-teaser--innovation-card anywhere in the rendered page (style variant never applied).
Evidence
Live curl of the card-grid container's mapping node (.6.json) confirms the mapping is well-formed; live curl of the policy node (.infinity.json) confirms correct titleType/cq:styleGroups; live curl of the rendered page's per-component debug comment shows a resolved policyPath of 'root/container/container/realmac/components/innovation-card' — which SKIPS the card-grid container's own intermediate nesting level present in both the actual content tree (root>container>container>container(card-grid)>card_0) and the mapping tree itself. The card-grid CONTAINER's own policy (one level shallower) DOES correctly apply (cmp-container--card-grid class present on its wrapper) — isolating the defect to specifically the doubly-nested innovation-card mapping entry.
Cause
AEM's Content Policy resolution for editable-template nested mappings appears to miscount/collapse a nesting level when an intermediate container level uses the same generic resourceType (realmac/components/container) as multiple ancestor levels used purely for responsive-grid layout. This is the same architectural class of defect as CQ-07 (same-resourceType at different nesting depths), not fully resolved by giving cards a distinct resourceType — the ambiguity has moved from the teaser level to the container level.
Recommended fix
Escalate to program_agent/human as an architecture-level decision (same class as CQ-04/CQ-07). Candidate approaches: (1) give the card-grid container itself a distinct resourceType/proxy so it is not visually identical, in resourceType terms, to the generic layout containers above it in the same mapping chain; (2) flatten the card-grid to be a direct child of a differently-typed structural region; (3) file/track as a known AEM platform limitation and accept a content-level workaround.

HIGH CQ-10 — titleFromPage/descriptionFromPage default to true when absent — cards show CTA text and page meta-description instead of their own authored copy

Issue
card_0 renders title="Learn More" (its single action's own text) instead of jcr:title="Tata Chemicals Innovation Centre", and description=the PAGE's own jcr:description (site-wide meta text) instead of its own jcr:description="Advanced materials and sustainable chemistry research...". Reproduced identically for all 4 cards (each shows its own action's text as the title). The hero teaser exhibits the SAME underlying mechanism but is not visibly wrong because its own jcr:title ("Innovation") happens to textually match the page's own jcr:title, and it authored no jcr:description of its own so the page-description fallback is the only content available.
Evidence
/content/realmac/us/en/innovation/jcr:content/root/container/container/container/card_0.json (raw JCR) shows jcr:title="Tata Chemicals Innovation Centre" correctly stored. .../card_0.model.json (Sling Model exporter) shows computed title="Learn More", description=the page's global jcr:description text. Disassembled com.adobe.cq.wcm.core.components.internal.models.v1.TeaserImpl.initProperties() via javap: titleFromPage = valueMap.get("titleFromPage", <pre-set field default>), and v2's constructor pre-sets that default to true before delegating to v1 — so when the property is absent from content (neither hero nor any card ever authors titleFromPage/descriptionFromPage), the effective default is TRUE, not FALSE. getTitle()'s fallback chain when titleFromPage=true and no linked page resolves: first action's own title, then current page's title — never the resource's own jcr:title.
Cause
Neither Designforge's dialog-specifications.md nor Blockwright's/Composer's authored content ever explicitly set titleFromPage="{Boolean}false"/descriptionFromPage="{Boolean}false" on any teaser/innovation-card instance, and Core Component v2 Teaser's undocumented-in-practice default (absent property => true) silently activates page/action-title fallback instead of the instance's own authored copy.
Recommended fix
Composer: add titleFromPage="{Boolean}false" and descriptionFromPage="{Boolean}false" explicitly to all 5 teaser/innovation-card content nodes (hero teaser, card_0, card_1, card_2, card_3) so each instance's own authored jcr:title/jcr:description is used as intended. Designforge should also record this dialog-default expectation in dialog-specifications.md / component-specifications.md for any future Core Teaser-based component.
